## 문제 인지 — "저장이 UX에 치명적일 만큼 느리다"

제가 다니는 회사의 MathCanvas는 선생님이 수학 교구를 배치해 수업 자료를 만드는 웹 캔버스입니다.
도형·수직선·쌓기나무 같은 교구를 놓고, 저장하면 서버에 올라갑니다.

저장할 때는 캔버스를 **한 장의 이미지로 찍어** 미리보기용으로 함께 올립니다.
목록에서 어떤 캔버스인지 알아볼 수 있어야 하니까요.

사용자 보고가 이렇게 왔습니다.

> *"저장이 UX에 치명적일 만큼 느리다."*

## 고민 — 체감을 먼저 수치로 바꿔야 했습니다

"느리다"는 티켓이 안 됩니다. 얼마나 느린지, 어디가 느린지 모르면 고칠 대상이 없습니다.

그리고 의심할 곳이 여럿이었습니다.

- 서버가 느린 걸까? (저장 API)
- 회선이 느린 걸까? (업로드)
- 아니면 브라우저에서 뭔가 무거운 걸 하고 있는 걸까?

세 곳 중 어디인지 모르면 서버 팀에 문의할지, 회선을 볼지, 코드를 볼지도 정할 수 없습니다.

## 실측 — 시간의 95%가 한 곳이었습니다

Playwright 로 저장 버튼 클릭부터 네트워크 요청 완료까지를 **구간별로 쪼개** 측정했습니다.
그리고 교구 종류에 따라 다를 것 같아 두 가지 캔버스로 비교했습니다.

| 캔버스 | 캡처 | 업로드 | 저장 API | **총** |
|---|---:|---:|---:|---:|
| 단순 (2D 교구) | 1,087ms | 465ms | 126ms | **1.7초** |
| **3D 교구 9개** | **9,608ms** | 366ms | 116ms | **10.1초** |

두 가지가 한 번에 확정됐습니다.

**첫째, 시간의 95%가 캡처 한 곳입니다.** 네트워크는 3D 에서도 0.5초뿐이었습니다.
서버·회선 문제가 아니었습니다.

**둘째, 교구 개수에 선형 비례합니다.** 2D 1.1초 → 3D 9.6초.
즉 교구를 더 놓을수록 저장이 선형으로 느려지는 구조였습니다.

> 재기 전에는 "서버에 물어봐야 하나" 싶었는데, 재고 나니 **문의할 필요가 없어졌습니다.**
> 측정의 첫 번째 값은 병목을 찾는 것이지만, 두 번째 값은 **엉뚱한 곳에 시간을 안 쓰게 하는 것**입니다.

## 원인 탐색 — 사진기가 아니라 받아쓰기를 하고 있었습니다

캡처는 `html-to-image` 의 `toPng` 를 쓰고 있었습니다. 이 방식은

- 화면의 **DOM 노드마다** 계산된 스타일을 읽어 문자열로 뽑아 인라인으로 박는다
- 3D 영역은 **한 번 더** 다시 그린다

### 💡 비유 — 방을 사진으로 남기는 두 가지 방법

| | 방법 | 비용이 어디에 |
|---|---|---|
| **받아쓰기** | 방 안 모든 물건의 재질·색·크기를 **말로 적고**, 그 설명서로 다시 그린다 | 물건 **개수**에 비례 |
| **사진** | 셔터를 누른다 | 해상도에 비례 |

`toPng` 는 받아쓰기입니다.

교구 하나가 수백 개 노드를 가지므로 **교구 수 × 노드 수** 만큼 받아쓸 항목이 늘어납니다.
선형 증가의 정체가 여기 있었습니다.

## 개선 — 새로 만들지 않았습니다

여기서 보통은 "더 빠른 캡처 라이브러리를 찾자"로 갑니다. 저도 그러려고 했습니다.

그런데 **같은 저장소의 학생 활동 미리보기**가 이미 같은 문제를 겪고 해결해 둔 상태였습니다.
코드 주석에 근거까지 남아 있었습니다.

> *과거 html-to-image(toPng)는 노드마다 계산된 스타일을 직렬화해 **약 2.8초**가 걸렸다.
> 대신 캔버스의 본질만 직접 직렬화·합성한다.*

### 💡 비유 — 옆 팀이 이미 닦아둔 길

같은 산을 넘어야 하는데, 저는 새 길을 뚫으려 했습니다.
그런데 옆 팀이 반년 전에 같은 산을 넘으면서 **길을 닦아 놨고, 이유까지 표지판에 적어** 뒀습니다.

제가 한 일은 그 길을 찾은 것과, **그 길을 두 팀이 함께 쓰도록 공용화**한 것입니다.
새로 만든 게 아닙니다.

그 기법을 공용 모듈로 추출해 저장 경로도 쓰게 했습니다.

## 개선 방법 — 세 가지를 각각 다르게 다룹니다

| | 옛 방식 | 새 방식 |
|---|---|---|
| 벡터 콘텐츠 | 노드별 스타일 직렬화 | **SVG 통째 직렬화** |
| 3D 교구 | 다시 그리기 | **라이브 화면 버퍼를 그대로 복사** |
| 펜 필기 | 복제본에 포함 | 별도 층으로 합성 |

3D 부분이 핵심입니다. **SVG 직렬화로는 3D 픽셀이 안 따라옵니다.**
직렬화는 `<canvas>` 태그만 복사하고, 거기 그려진 픽셀은 못 가져옵니다.

그래서 라이브 화면을 그대로 오려 붙입니다.

```ts
// 3D 렌더러가 preserveDrawingBuffer 를 켜 둬 마지막 프레임이 버퍼에 남아 있다
ctx.drawImage(liveCanvas, x, y, w, h)
```

### 💡 비유 — 옮겨 그리기 vs 오려 붙이기

3D 부분을 "다시 그린다"는 건 **그림을 보고 옮겨 그리는 것**입니다. 시간이 걸립니다.

"버퍼를 복사한다"는 건 **이미 인쇄된 종이를 그대로 오려 붙이는 것**입니다.
어차피 화면에 이미 그려져 있으니, 다시 그릴 이유가 없습니다.

## 결과

| 캔버스 | 캡처 (전 → 후) | 총 저장 (전 → 후) |
|---|---|---|
| 단순 (2D) | 1,087ms → **110ms** (약 10배) | 1.7초 → 0.77초 |
| **3D 교구 9개** | 9,608ms → **141ms** (약 68배) | **10.1초 → 0.56초** (약 18배) |

가장 중요한 건 마지막 줄이 아니라 이것입니다.

**교구 개수에 대한 선형 의존이 사라졌습니다.** 2D 110ms vs 3D 141ms 로 거의 같아졌습니다.
즉 교구를 더 놓아도 저장이 느려지지 않습니다.

부수 효과로 코드도 줄었습니다.

| 파일 | 줄 수 |
|---|---|
| 저장 캡처 | 351 → **115** |
| 학생 활동 캡처 | 331 → **199** (중복 132줄 제거) |
| 자동 저장 | 209 → **140** (실행되지 않던 코드) |
| 외부 의존성 | `html-to-image` **제거** |

## 성능 개선이 기능 제약을 풀었습니다

이 작업은 원래 다른 기능의 파생이었습니다. **선생님이 풀이 과정을 녹화하는 기능**입니다.
녹화에 들어가려면 캔버스를 먼저 저장해야 했는데, 저장이 10초면 두 가지가 불가능했습니다.

**① 팝업 차단** — 브라우저는 사용자 클릭 직후 약 5초 안에만 새 창 열기를 허용합니다.
10초짜리 저장이 끝난 뒤에는 창이 차단됩니다.

### 💡 비유 — 문이 닫히기 전에 들어가야 합니다

브라우저는 "사용자가 방금 클릭했으니 이 창은 사용자 의도다"라고 판단해 문을 열어줍니다.
그 유효 시간이 약 5초입니다. 10초 걸리는 일을 먼저 하면 **문이 이미 닫혀 있습니다.**

0.56초가 되면서 "저장 → 새 창" 순서가 가능해졌습니다.

**② 백그라운드 탭 정지** — 차단을 피하려고 창을 먼저 열면 원래 탭이 백그라운드가 됩니다.
그러면 브라우저가 화면 갱신 루프를 멈춰서 **캡처가 끝나지 않습니다.**
순서를 바꿔 이 문제를 구조적으로 제거했습니다.

> 성능 개선이 단순한 체감 향상이 아니라 **기능 설계의 선택지를 열었습니다.**
> "빠르게 만들기"가 목적이 아니라, 느려서 못 하던 걸 하게 만드는 게 목적이었습니다.

## 배운 것

### 계측이 가설을 네 번 뒤집었습니다

이 작업에서 **눈과 추론으로 내린 진단이 네 번 틀렸습니다.** 매번 측정이 바로잡았습니다.

| 추론 | 측정 결과 |
|---|---|
| "미리보기에 3D 교구가 안 담긴다" | 캡처는 정상. 목록의 `object-fit: cover` 가 양옆을 자른 것 |
| "그 교구는 3D다" | `<canvas>` 0개 — 순수 SVG였다 |
| "학생 활동도 같은 캡처 코드를 쓴다" | 호출부 1곳뿐. 학생 활동은 **331줄짜리 별도 구현** |
| "동료 브랜치가 깨져 있다" | 내가 방금 지운 패키지가 의존성 폴더에서 빠져 생긴 오염 |

세 번째가 특히 뼈아팠습니다. **그 "별도 구현"이 제가 찾아야 했던 정답지**였습니다.
작업 전에 같은 일을 하는 코드를 `grep` 으로 열거했다면 처음부터 그것을 재사용했을 겁니다.

첫 번째도 창피합니다. 60×40 크기의 작은 미리보기를 **눈으로만 보고** "캡처가 3D를 못 담는다"고
보고했습니다. 실제로는 16:9 이미지를 3:2 칸에 넣으면서 양옆이 잘린 것이었고,
게다가 그 교구는 3D도 아니었습니다.

이후 원칙으로 굳혔습니다.

> **증상을 보면 원인을 말하기 전에, 같은 일을 하는 구현과 호출부를 먼저 세라.**
> "하나뿐"이라는 가정이 가장 자주 틀린다.
> 그리고 **축소된 결과물로 판단하지 말고 원본 크기로 저장해서 봐라.**

### 타입 검사와 테스트가 통과해도 빌드는 깨질 수 있습니다

안 쓰는 의존성을 제거했을 때 타입 검사(기존 47건 유지)와 테스트(1,742건 통과)는 모두 초록이었습니다.

**빌드는 깨졌습니다.**

번들러의 수동 청크 설정 3곳에 그 패키지가 진입점으로 박혀 있었습니다.
**설정 파일은 타입 검사·테스트 어느 쪽의 시야에도 없습니다.**

### 리팩터링 중 놓친 동작을 기존 테스트가 잡았습니다

중복 제거로 코드를 옮기며 두 가지를 빠뜨렸는데, 기존 회귀 테스트가 잡아냈습니다.

- 일반 문서 환경에서는 스타일 수집을 **건너뛰어야** 한다
  (앱 CSS 전체를 인라인하면 오히려 느려진다)
- 격리 영역 스타일에서 `@font-face` 와 외부 `url()` 을 **제거해야** 한다
  (외부 자원을 물면 이미지 추출이 통째로 실패한다)

둘 다 복원하자 **오히려 더 빨라졌습니다** (0.79초 → 0.56초).

## 검증 방식

- **성능** — Playwright 로 클릭→요청 구간을 쪼개 측정. 단순/3D 두 캔버스로 전·후 대조
- **화질** — 캡처 결과를 **원본 크기 PNG 로 저장해 눈으로 대조** (축소본으로 판단해 오진한 전례가 있어서)
- **회귀** — 옛 방식 재도입 차단, 3층 합성 유지, 가려진 탭에서도 완료되는지 — 테스트 8건
- **변이 실험** — 가드가 실제로 잡는지 확인 (순서를 뒤집어 테스트가 빨개지는 것을 확인)
- **빌드** — 메인·SDK 두 빌드 모두 통과
