> 수학 교구 캔버스 서비스(MathCanvas)의 학생 답안 히스토리 저장 최적화.
> **설계 → TDD 구현 → 실측 → 재설계 3회 → 실측 검증**을 하루에 압축한 프로젝트.
> Stack: TypeScript · Vue 3 · Pinia · Vitest · fflate

## 문제 — 조작이 쌓일수록 저장이 무거워졌다

학생이 캔버스에서 교구를 조작한 과정(`historyStack`)은 교사가 학생 풀이 과정을 재생하는 데 쓰이는 핵심 데이터다. 그런데 저장 구조가 **매 조작마다 관련 객체의 변경 전/후 전체를 deep-clone**하는 방식이라:

- 3D 교구 활동에서 답안 히스토리가 **3.7MB**까지 증가 — 전송 캡(500KB)을 초과하면 재생 보조 데이터가 잘려나갔다.
- 조작이 많을수록 선형으로 증가 → 서비스 확장 시 저장/전송 비용 리스크.
- 제약: **재생 엔진(약 1,100줄)과 23개 교구 모듈은 절대 손대면 안 됨**(교사 풀이 재생을 그대로 지켜야 함), 백엔드 스키마 변경 불가.

## 접근 — 저장 경계에서만 변환하는 순수함수

핵심 아키텍처 결정은 하나였다: **변환을 "저장 경계의 순수함수"로 격리한다.**

```
세션 중:   historyStack = 기존 그대로 (full 스냅샷, 무변경)
저장 직전: deflate(순수함수)  → 델타 + gzip
로드 직후: hydrate(순수함수)  → full 복원 → 기존 재생 엔진에 그대로 투입
```

- 앱 내부(조작·undo·재생)는 항상 full 데이터만 본다 → **재생 코드 무수정, 회귀 위험 원천 차단.**
- 순수함수라 `hydrate(deflate(x)) ≡ x` — **왕복 동일성을 자동 테스트로 기계 보증(복원 동일성 spec 27케이스).** 이후 인코딩 엔진을 세 번 갈아엎어도 이 게이트가 안전망으로 남았다.

조작이 쌓일수록 개선 전(주황)은 선형으로 치솟지만, 개선 후(파랑)는 거의 평탄하다 — 변경분만 기록하기 때문이다. (점 위에 커서를 올리면 시점별 수치가 보인다.)

## 실측이 설계를 두 번 뒤집었다

인코딩은 3층으로 쌓았는데, **각 층은 앞 층의 실측 실패에서 나왔다.** 이게 이 프로젝트의 진짜 이야기다.

**① 델타 — 변경분만 기록 (초기 설계)**
객체별 last-seen 해시맵과 비교해 바뀐 필드만 저장, 못 잡으면 full 폴백. 합성 벤치마크로 **17×** 절감을 확인하고 자신 있게 붙였다.

**→ 반전 #1: 합성 17×가 실제 1.1×로 무너졌다.**
실제 payload를 계측하니 절감이 거의 없었다. 노드/필드별 크기 분포를 찍어보니, **부피의 95%가 "조작 노드"가 아니라 캔버스 전체 스냅샷(init/refresh 컨테이너)** 이었다. 조작 하나하나는 이미 작았고, 진짜 짐은 시작상태·다시풀기 기록에 통째로 박힌 캔버스 복사본이었다. 합성 데이터가 이 분포를 재현하지 못한 것.

**② 컨테이너 델타 — 전체 스냅샷의 내부 배열까지 재귀 (반전 후 재설계)**
그래서 컨테이너 스냅샷 노드의 내부까지 델타를 재귀 적용하고, 남는 건 gzip으로 눌렀다. **5~10×** 로 올라왔다.

**→ 반전 #2: init은 델타의 이론적 한계였다.**
"첫 등장 = 비교 기준이 없음"이라 최초 스냅샷은 델타로 접을 수가 없다. 여기서 손실 최적화(init 자체 생략, synthetic 재구성 의존)를 검토했지만 **비가역적 정보 손실**이라 배제하고, 대신 무손실 gzip(포맷 v3)으로 최초 1회분까지 압축했다.

**→ 반전 #3: gzip으로도 3D 답안은 167~257KB가 남았다.**
2차원 활동은 잘 눌렸는데 3D 교구 답안은 여전히 무거웠다. gzip이 뒤섞인 3D 좌표를 못 눌렀기 때문. **"재생이 실제로 무엇을 읽는가"를 코드 감사**로 파고든 결과가 마지막 층이다.

**③ 소비-기반 strip — 재생이 읽지 않는 필드 제거 (화이트리스트 1개)**
3D 직렬화의 **~95%가 THREE.js 렌더링 기계 통째**(`customElementInstance` — 꼭짓점 좌표 수백 개, 면·모서리, 카메라, 렌더러)였는데, 재생은 이걸 꺼내 쓰지 않고 **설계도(위치·회전·슬라이더 값)만 읽어 모형을 처음부터 재조립**한다. 이 필드 하나를 소비-기반 감사로 특정해 strip → **237~412×**.

> 단계별 기여: 델타만 **1.1×** → 컨테이너+gzip **5~10×** → 소비-기반 strip **237~412×**. 진짜 도약은 압축이 아니라 "안 읽는 데이터"를 증명해 지운 데서 나왔다.

## 핵심 — "설계도 vs 완성품", 그리고 지워도 되는 증명

3D 교구 저장분에는 두 종류가 섞여 있었다.

- **① 설계도 (~5%, 몇 백 바이트)** — "삼각뿔, 위치 (320,180), 회전 15°, 전개 슬라이더 50, 카메라 각도 …"
- **② 완성품 (~95%, ~50KB)** — ①로 만들어진 THREE 렌더링 결과물 통째

②를 지워도 된다는 근거 세 가지:

1. **재생은 ①만 읽는다.** 재생 버튼은 설계도를 읽어 모형을 새로 조립한다. 저장된 ②를 소비하는 코드는 코드베이스 어디에도 없음을 **전수 코드 감사**로 확인.
2. **②는 애초에 "기록"이 아니었다.** 화면에 살아있는 DOM/WebGL 객체라 `cloneDeep`이 복제하지 못하고, 실제로 담긴 건 과거 사본이 아니라 **"지금 화면의 그것"을 가리키는 라이브 참조**였다. 1번째 기록의 ②도 20번째의 ②도 동일한 현재 화면을 가리킴 — 과거 기록으로 기능한 적 없는 순수한 짐.
3. **같은 원리가 이미 프로덕션 검증돼 있었다.** 교사↔학생 실시간 동기화(발표자 미러링)가 처음부터 "설계도만 전송 → 받는 쪽이 조립"으로 동작 중이었고, **동일 필드를 이미 strip**하고 있었다. 새 이론이 아니라 검증된 원리를 저장 경로에 적용한 것.

여기서 두 가지 트레이드오프를 명시적으로 판단했다:
- **init 생략(손실) 배제** — "롤백하면 된다"가 저장된 데이터엔 성립하지 않으므로, 비가역 손실은 안 됨 → 무손실 gzip으로 해결.
- **strip은 바이트-무손실이 아닌 "의미-무손실"** — 왕복 spec 계약을 `복원본 ≡ strip(원본)`으로 갱신하고, 자동 테스트가 못 덮는 영역은 **재생 3단계 실검증을 필수 게이트**로 통과.

## 제약을 포맷 설계로 흡수

- **백엔드 무변경**: `[{"__hv":3,"z":"<gzip+base64>"}]` — 단일 원소 **배열** 형태를 유지해 기존 스키마(`historyJson: array`)와 완전 호환.
- **동기 경로 제약**: 저장 경로 3개 중 `unload`-keepalive가 동기 문맥이라, 비동기 `CompressionStream` 대신 **fflate 동기 API**를 채택해 3경로 전부 커버.
- **하위호환**: 읽기는 v1(원본)/v2(델타)/v3(델타+gzip) 일괄 지원, 쓰기는 v3만 — 기존 저장분 무중단.
- **정확도 우선**: 압축 이득이 없는 소형 데이터는 자동으로 v2 폴백(무리한 압축 안 함).

## 안전장치

- 복원 동일성 spec **27케이스** — 제거 대상은 화이트리스트로 spec에 박제
- 교사 재생(재생·프레임 이동·슬라이더) **3단계 개선마다 실사용 검증**
- 기존 저장분(옛 형식) 그대로 읽힘 — 하위호환
- 판정이 애매한 데이터는 압축하지 않고 통째 저장
- 전체 단위 테스트 **1,101개 PASS** (신규 실패 0)

## 같은 원리를 저장 파이프라인 전체로 확장

"설계도만 남기기"는 히스토리에만 유효한 게 아니었다. 완성품이 드나드는 나머지 문 3곳을 감사로 찾아 잠갔다.

- **① 캔버스 저장본(projectJson)** — 뷰어·슬라이드가 매번 내려받아 여는 파일에도 완성품이 실렸다. 직렬화 이전 체크포인트에 strip을 걸어 THREE `toJSON` **CPU 연산까지 제거**. 실측 48.0KB → 18.7KB, 저장 버튼 반응도 가벼워짐.
- **② 답안의 최종 상태(elements)** — 조작 과정은 압축했지만 "최종 화면 상태"가 여전히 완성품을 싣고 있었음을 감사가 발견 → 같은 경계에 한 줄로 마감.
- **③ 레거시 격리** — 옛 형식 저장본을 열 때 완성품 덤프가 세션 메모리에 상주하던 경로 차단.

이 확장은 히스토리보다 조건이 더 좋았다: **저장본에서 해당 필드를 읽는 소비자가 0개**(정적 감사)라, 버전링/하위호환 처리 자체가 불필요했다.

## 배운 것

1. **합성 벤치 PASS ≠ 실제 성공.** 합성 17×가 실제 1.1×로 무너졌고, 실제 payload 계측 + 노드/필드별 분포 진단이 진짜 병목(컨테이너 스냅샷)을 찾아줬다. 이후 fixture를 실제 데이터 shape으로 재생성했다.
2. **저렴한 게이트를 먼저 깔면 실험이 빨라진다.** 왕복 동일성 spec을 1일차에 심어두니, 인코딩 엔진을 세 번(델타→컨테이너→gzip) 갈아엎으면서도 회귀 공포 없이 반복할 수 있었다.
3. **최적화의 경계는 "가역성"으로 긋는다.** 코드 롤백이 가능한 변환(압축)과 불가능한 결정(저장 데이터의 정보 손실)을 구분해, 후자는 배율이 아쉬워도 배제.
4. **압축의 다음 단계는 "무엇이 데이터인가"의 재정의.** gzip이 정보이론 한계에 닿았을 때, 소비자(재생 엔진) 관점의 감사가 "애초에 실을 필요 없는 95%"를 찾아냈다. 압축률 튜닝보다 데이터 계약 재검토가 더 큰 지렛대였다.
5. **"안 하기로 한 결정"도 산출물이다.** 후보 4개를 실측으로 추려 2개만 적용, 2개는 근거와 함께 배제(이득 0 / 이미 최적)하고 그 판단 근거를 문서에 남겨 미래의 재시도 비용을 없앴다.
