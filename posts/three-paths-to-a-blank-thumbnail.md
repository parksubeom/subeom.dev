교육용 수학 학습 도구를 만들고 있습니다. 선생님이 수업 자료를 만들면 학생이 태블릿으로 풀고 선생님은 나중에 **활동 리포트**에서 학생별로 무엇을 했는지 확인합니다. 이 리포트에는 슬라이드마다 작은 썸네일이 붙습니다 — 그 학생의 화면이 어떤 모습이었는지 보여주는 그림입니다.

그 썸네일이 여러 방식으로 비어 있었습니다. 세 갈래로 갈려 보였는데 원인은 하나였고 고치는 도중에 제가 새 백지를 하나 더 만들었습니다.

---

## 한 줄

썸네일이 백지로 나오는 세 가지 경로를 추적해 고쳤습니다. 셋 다 **화면을 만드는 코드가 서버 응답의 일부만 읽고 나머지를 버리는** 같은 원인이었습니다. 원인 가설 하나가 실제 데이터 앞에서 완전히 뒤집혔고, 수정 도중 제가 만든 회귀는 화면을 직접 열어본 뒤에야 잡혔습니다.

---

## 1. 받은 것

기획에서 세 건이 왔습니다.

- 썸네일을 못 그리는 경우가 없어야 한다
- 페이지별 보기 카드가 캔버스를 제대로 담지 못한다
- 활동이 없는 캔버스에 `활동 보기` 버튼이 활성화된다

셋 다 "썸네일 근처"라는 것 말고는 공통점이 안 보였습니다.

---

## 2. 카드가 캔버스를 반쯤 자르고 있었다

썸네일 박스 높이가 고정이었습니다.

```html
<div class="relative h-[114px] w-full overflow-hidden ...">
```

카드 폭은 화면 크기에 따라 변하는데 높이만 `114px` 로 묶여 있었습니다. 캔버스는 16:9 입니다. 폭에 맞춰 그리면 높이가 얼마여야 하는지 계산해 봤습니다.

| 화면 | 썸네일 폭 | 16:9 라면 | 실제 | 잘린 양 |
|---|---|---|---|---|
| 태블릿(2열) | 328px | 184px | 114px | **-38%** |
| 노트북(2열) | 428px | 241px | 114px | **-53%** |
| 데스크탑(3열) | 343px | 193px | 114px | **-41%** |
| 와이드(3열) | 443px | 249px | 114px | **-54%** |

축소 로직이 `max(폭 비율, 높이 비율)` 이라(CSS의 `object-fit: cover` 와 같은 동작) 폭을 채우려고 그림을 확대하고 넘친 위아래를 `overflow-hidden` 이 잘랐습니다. **캔버스 절반이 사라지고 있었습니다.**

`aspect-video` 로 바꿔 높이가 폭을 따라오게 했습니다.

## 3. 활동 판정 — 가설이 데이터 앞에서 뒤집혔다

`활동 보기` 버튼은 이 판정을 씁니다. 학생이 캔버스에 뭔가를 했는지 조작 기록으로 세는 함수입니다.

```ts
export function hasMathCanvasHistoryStackForReplay(projectState: unknown): boolean {
  const hs = (projectState as { historyStack?: unknown }).historyStack
  if (!Array.isArray(hs) || hs.length === 0) return false
  return hs.some((item: any) => String(item?.type).toLowerCase() !== 'init')
}
```

리포트 한 줄은 선생님이 만든 원본과 학생이 낸 답을 합쳐서 만듭니다.

```ts
const merged = { ...template, ...learner }
```

그래서 이렇게 짐작했습니다. **학생이 아무것도 안 해도 선생님 쪽 조작 기록이 물려받아지고 그게 "활동 있음"으로 세어진다.**

말이 되는 설명이었습니다. 그런데 로컬 서버에 붙어 실제 응답을 찍어보니 이랬습니다.

```
선생님 원본:     조작 기록 없음
학생 7명 전원:   1개, 타입은 undefined
```

**원본에는 기록이 아예 없었습니다.** 짐작이 틀렸습니다. 그리고 학생 전원이 똑같이 "노드 1개, 타입은 `undefined`" 였습니다.

조작 기록은 용량을 아끼려고 압축해서 저장합니다. 압축하면 통째로 노드 하나가 되고 그 노드엔 조작 종류가 없습니다.

```ts
[{ __hv: 3, z: 'H4sIAAAAA...' }]   // 압축본 — type 이 없다
```

```ts
String(undefined).toLowerCase() !== 'init'   // "undefined" !== "init" → 항상 true
```

**압축을 안 풀고 세는 바람에, 캔버스에 들어가기만 해도 전원이 "활동 있음"이 됐습니다.**

학생 화면은 같은 함수를 쓰는데 왜 맞았을까요. 그쪽은 **이미 풀린** 기록을 넘기고 있었습니다. 그래서 "버튼은 눌리는데 들어가면 활동 내역이 없어요"가 됐습니다. 두 화면이 같은 판정을 쓰면서 서로 다른 답을 낸 이유가 함수가 아니라 입력의 차이였습니다.

```ts
let stack = raw
if (isDeflatedHistoryStack(raw)) {
  try { stack = hydrateHistoryStack(raw) }
  catch { return false }              // 못 풀면 판정 포기 — 옛 오판으로 돌아가지 않게
}
return stack.some((item: any) => {
  const t = item?.type
  return typeof t === 'string' && t.toLowerCase() !== 'init'   // 문자열일 때만 센다
})
```

같은 판정을 쓰는 학생별 보기 화면도 함께 고쳐졌습니다.

## 4. 제가 새 백지를 만들었다

"카드를 목록 화면의 카드처럼 바꿔라"를 받고 그 카드들이 **서버가 미리 구워 둔 이미지**를 쓴다는 걸 확인했습니다. 그래서 두 가지를 넣었습니다.

- 캔버스가 아닌 타입은 선생님 원본 페이지를 썸네일에 넘긴다
- 서버 이미지가 있으면 그것을 우선 쓴다

화면을 열어보니 OX 퀴즈 카드가 텅 비었습니다. 문제 문구 자리에 `질문을 입력해 주세요.` 라는 안내 문구가 뜨고 학생이 고른 답에 붙던 표시가 사라졌습니다.

썸네일의 목적을 잘못 읽었습니다. 이 화면의 썸네일은 **그 학생의 최종 상태**를 저장된 데이터로 다시 그리는 것입니다. 선생님 원본만 넘기면 학생 답이 없고, 서버 이미지로 갈아치우면 다시 그리는 일 자체가 사라집니다.

되돌렸습니다. 16:9 비율만 남겼습니다 — 그게 원래 문제였습니다.

---

## 5. 일반 슬라이드 백지 — 빈 값이 이겼다

되돌리고 나니 이번엔 일반 슬라이드가 백지가 됐습니다. 다시 찍어봤습니다.

```
선생님 원본     내용 = 배열(2개)   ← 이미지 + 텍스트
학생 8명 전원   내용 = 배열(0개)
```

일반 슬라이드는 학생이 손댈 게 없어서 응답이 빈 배열로 옵니다. 그런데 합칠 때 학생 값을 우선하니 **빈 배열이 선생님 내용을 덮어썼습니다.** 선생님이 그린 도화지 위에 학생의 백지를 얹은 셈입니다.

OX 퀴즈나 선지형은 내용이 객체라 필드별로 합쳐져 이 구멍에 안 걸렸습니다. 그래서 일반 슬라이드만 깨져 보였습니다.

같은 상황을 막는 코드가 **선지형에는 이미 있었습니다.**

```ts
// 학습자 contents가 options: [] 로 템플릿을 덮은 경우 정답 메타 복구
if ((!Array.isArray(merged.options) || merged.options.length === 0) && ...) {
  merged.options = template.options.map((o: any) => ({ ...o }))
}
```

일반 슬라이드에도 같은 처방을 적용했습니다. 학생이 실제로 그린 게 있으면 여전히 학생 것이 이깁니다.

## 6. 배경색이 통째로 증발했다

배경색을 지정한 페이지가 썸네일에서 흰 바탕으로 나왔습니다. 학생 화면에서는 제대로 나왔습니다.

배경색은 내용 안이 아니라 **페이지 자체**에 붙어 옵니다.

```
pages[] = { id, data, order, type, backgroundColor, memo, ... }
                                   ↑ 여기
```

슬라이드 종류와 무관한 공통 속성이니 맞는 설계입니다. 일반 슬라이드의 내용은 객체 배열이라 배경색을 끼워 넣을 자리도 없습니다.

합치는 함수는 양쪽의 내용만 읽고 있었습니다. 슬라이드 종류만 예외적으로 따로 챙기고 나머지 페이지 레벨 속성은 손도 안 댔습니다. 그래서 배경색과 메모가 사라졌습니다.

학생 화면이 쓰는 변환은 처음부터 둘을 나눠 챙깁니다.

```ts
const spread = type === GENERAL ? { contents: raw } : { ...raw }   // 내용
return { ...spread, id, type, backgroundColor, memo, thumbnail }   // 페이지 레벨
```

**리포트 쪽만 이 규칙을 안 따르고 있었습니다.**

---

## 7. 셋이 하나였다

고치고 나서 보니 원인이 하나였습니다.

| | 놓친 것 | 증상 |
|---|---|---|
| 1 | 학생 빈 배열이 원본을 덮음 | 일반 슬라이드 백지 |
| 2 | 배경색·메모 | 배경색 안 나옴 |
| 3 | 압축 기록을 안 품 | 활동 없는데 "활동 보기" |

셋 다 **합치는 코드가 내용만 보고 페이지 레벨을 놓친다**는 한 문장으로 설명됩니다. 증상이 셋으로 갈려 보였을 뿐입니다.

---

## 8. 손대지 않은 캔버스는 무엇을 보여주나

캔버스는 저장된 데이터로 다시 그릴 수 없어서 이미지가 필요합니다. 학생 화면은 **조작이 있을 때만** 사진을 찍습니다.

```ts
/**
 * → 조작 없이 보기만 했거나 갓 진입한 슬라이드는 캡처를 건너뛰고 원본 썸네일을 유지.
 */
function isCanvasUntouched(root: CaptureRoot): boolean { ... }
```

의도된 설계입니다. 그런데 **유지할 원본을 아무도 연결하지 않아서** 백지가 됐습니다.

서버는 이미지가 필요한 두 타입에만 대표 그림 주소를 채워 보냅니다. 썸네일 컴포넌트는 대체 그림을 이미 지원하고 있었고 리포트만 안 넘겼습니다. 연결했습니다.

```
학생 그림 → 없으면 선생님 원본 → 그것도 없으면 안내 문구
```

## 결과

세 상태가 화면에서 갈립니다.

| 상태 | 썸네일 | 배지 |
|---|---|---|
| 조작함 | 학생이 그린 그림 | 활동 보기 |
| 방문했지만 조작 안 함 | 선생님 원본 | 활동 없음 |
| 방문 안 함 | 선생님 원본 | 활동 없음 |

아래 두 줄은 썸네일이 같지만 배지와 머문 시간이 다릅니다. **썸네일은 "화면이 어떤 모습이었나", 배지는 "학생이 뭘 했나"** — 두 신호를 분리해 두기로 했습니다.

| | |
|---|---|
| 유닛 테스트 | 1,923 → **1,948건 전부 통과** |
| 타입 오류 | 36건 유지 (증가 0) |
| 신규 테스트 | 20건 (활동 판정 8 · 합치기 9 · 대체 그림 배선 3) |

## 배운 것

### 코드만 읽고 세운 가설이 데이터 앞에서 뒤집혔다

| 추론 | 측정 결과 |
|---|---|
| "합치는 과정에서 선생님 기록이 물려받아져 활동으로 세어진다" | 원본엔 기록이 **아예 없었다**. 원인은 압축 미해제 |
| "활동 응답에 대표 그림 주소가 안 온다" | 이미지가 필요한 두 타입에는 **온다**. 일반 슬라이드 샘플 하나만 보고 단정했다 |
| "일반 슬라이드의 체크 표시는 정답 오표시다" | **열람 확인** 표시였다. 내부 상태 이름이 `'correct'` 라 오독했다 |

세 번 다 그럴듯했고 세 번 다 틀렸습니다. 합치는 구조를 읽고 세운 가설은 특히 설득력이 있었는데, 실제 응답 한 줄이 그걸 무너뜨렸습니다.

원칙으로 굳혔습니다. **원인을 말하기 전에 그 데이터를 직접 찍어 본다.** 코드는 무엇이 가능한지 알려주지만 무엇이 실제로 오는지는 알려주지 않습니다.

### "A 처럼 만들어라"는 A 의 목적부터 확인한다

목록 카드를 흉내 내면서 방식(서버 이미지)까지 베꼈다가, 이 화면의 썸네일이 존재하는 이유 자체를 지웠습니다. 목록 카드의 이미지는 "저장된 결과를 보여준다"이고, 리포트 카드는 "학생의 최종 상태를 다시 그린다"였습니다. 겉모습은 비슷해도 하는 일이 다릅니다.

### 통과하는 테스트는 아무것도 보장하지 않는다

고칠 때마다 **고친 걸 도로 빼서 테스트가 실패하는지** 확인했습니다.

| 고침 | 되돌렸을 때 실패한 테스트 |
|---|---|
| 활동 판정 | 3건 |
| 일반 썸네일 | 1건 |
| 배경색 | 3건 |
| 정렬 제거 | 1건 |

아무것도 검사하지 않는 테스트도 초록으로 통과합니다. 실패하는 걸 봐야 그 테스트가 무엇을 잡는지 알 수 있습니다.

### 같은 판정이 두 화면에서 다른 답을 내면 입력을 의심한다

리포트와 학생 화면이 **같은 함수**를 쓰면서 반대 결론을 냈습니다. 함수를 의심하기 쉬운 상황인데 문제는 넘기는 값이었습니다 — 한쪽은 압축본을, 한쪽은 풀린 값을 줬습니다. 공용 판정 함수를 만들 때 입력의 상태까지 계약에 넣어야 한다는 걸 배웠습니다.

## 검증 방식

- 로컬 서버에 붙여 **실제 응답을 찍어 대조** — 가설 세 개가 여기서 뒤집혔습니다
- 고침마다 **되돌렸을 때 실패하는지** 확인
- 공용 썸네일 컴포넌트를 쓰는 **11곳을 전수 확인**한 뒤 변경
- 화면 확인 — 제가 만든 회귀는 여기서만 잡혔습니다
